## Technical Specification: iDar Device Register Protocol (DDRP v0.1)

**Layer:** Control and Authentication Plane over DCLP / UDP

**Framework:** Perseo-Piscis Standard | DENSA Network

**Manager:** VANGUARD (_The Bouncer_)

---

### 1. Transport Model Without a Web Layer

DDRP does not run any web server, nor does it use REST, JSON, classic TLS, or HTTP headers.

- **Channel:** It runs encapsulated directly inside **DCLP (iDar Caravan Link Protocol)** packets using UDP sockets on the default port **`6767`** (or a configurable control port).

- **Base Header:** Every DDRP packet travels preceded by the 16-byte binary `DCLPHeader`.
- **Pre-Tunnel Security:**
- The DDRP payload is authenticated via a signature or an HMAC-SHA256 derived from the symmetric key of the enrollment token (`enrollment_token`).
- There is no negotiation of X.509 certificates or `POST`/`GET` requests. Only flat binary structures in memory packed in network byte order (_Big-Endian_).

### 1.1 Out-of-Band (OOB) Token Provisioning

The `enrollment_token` is an external 32-byte pre-shared secret (PSK) and is never transmitted over the wire. It must be provisioned prior to registration through one of the following channels:

- **Workstations / Servers (`0x01`, `0x02`):** Stored in a restricted filesystem path (`/etc/densa/enrollment.key`, mode `0600`) or supplied via the `DENSA_ENROLLMENT_TOKEN` environment variable.
- **Mobile (`0x03`):** Scanned via a one-time QR code generated by the VANGUARD management interface.
- **Edge / Embedded (`0x04`):** Burned into non-volatile secure storage (e.g., TPM, Secure Element, or factory EEPROM) during image staging.

### 2. Packet Structure in Memory (`ddrp.h`)

Inheriting the packet identifiers from Laniakea (`PKT_JOIN_*`), DDRP defines 4 types of binary packets to complete registration and coordinate delivery:

```c
/* SPDX-License-Identifier: GPL-2.0-only
 * Perseo-Piscis / DENSA - DDRP Specification
 */

#ifndef DDRP_H
#define DDRP_H

#include <stdint.h>

/* DDRP Packet Types */
typedef enum {
    DDRP_PKT_SOLICIT   = 0x01, /* Device requests to join DENSA */
    DDRP_PKT_CHALLENGE = 0x02, /* VANGUARD responds with a nonce/challenge */
    DDRP_PKT_RESOLVE   = 0x03, /* Device delivers cryptographic response */
    DDRP_PKT_ASSIGN    = 0x04, /* VANGUARD confirms delivery of LCoord and WireGuard */
    DDRP_PKT_REJECT    = 0x0E  /* Rejection due to invalid token or lack of capacity */
} DDRPPacketType;

/* Device Types */
typedef enum {
    DEV_TYPE_CORE        = 0x00, /* VANGUARD Nodes */
    DEV_TYPE_SERVER      = 0x01, /* Servers / Video Streaming */
    DEV_TYPE_WORKSTATION = 0x02, /* Laptops / PCs */
    DEV_TYPE_MOBILE      = 0x03, /* Cell phones / Lightweight clients */
    DEV_TYPE_EDGE        = 0x04, /* IoT / Embedded nodes */
    DEV_TYPE_GUEST       = 0x99  /* Isolated clients (WAN only) */
} DDRPDeviceType;

/* Perseo-Piscis / Laniakea Topological Coordinate */
typedef struct __attribute__((packed)) {
    uint32_t x; /* Quadrant / Functional role (IPv6 Subnet) */
    uint32_t y; /* Ordinal node identifier in the grid */
} DDRP_LCoord;

/* -------------------------------------------------------------
 * 1. SOLICIT: The node knocks on VANGUARD's door
 * ------------------------------------------------------------- */
typedef struct __attribute__((packed)) {
    uint8_t     device_type;     /* DDRPDeviceType */
    uint8_t     flags;           /* Bit 0: Requests Internet access (WAN Gateway) */
    uint16_t    preferred_port;  /* Local port for WireGuard (e.g. 51820) */
    uint8_t     client_pubkey[32]; /* Client Curve25519 public key */
    uint8_t     token_hash[32];  /* SHA256(enrollment_token) for pre-identification */
    char        hostname[32];    /* Human-readable network name (null-terminated ASCII) */
} DDRP_MsgSolicit;

/* -------------------------------------------------------------
 * 2. CHALLENGE: VANGUARD responds with an anti-replay challenge
 * ------------------------------------------------------------- */
typedef struct __attribute__((packed)) {
    uint8_t     nonce[32];       /* Unique pseudorandom number */
    uint32_t    challenge_id;    /* Correlative registration session ID */
} DDRP_MsgChallenge;

/* -------------------------------------------------------------
 * 3. RESOLVE: The device signs the nonce proving possession
 * ------------------------------------------------------------- */
typedef struct __attribute__((packed)) {
    uint32_t    challenge_id;    /* Same ID delivered by VANGUARD */
    uint8_t     hmac_proof[32];  /* HMAC_SHA256(Key=enrollment_token, Data=nonce) */
} DDRP_MsgResolve;

/* -------------------------------------------------------------
 * 4. ASSIGN: VANGUARD injects coordinates and link parameters
 * ------------------------------------------------------------- */
typedef struct __attribute__((packed)) {
    uint32_t    challenge_id;
    DDRP_LCoord assigned_coord;  /* Assigned X, Y coordinates */
    uint8_t     assigned_ipv6[16];/* Computed fd00:densa:X:0::Y */
    uint8_t     gateway_pubkey[32];/* VANGUARD WireGuard key */
    uint16_t    gateway_port;    /* Gateway WireGuard port */
    uint32_t    lease_seconds;   /* Registration duration before heartbeat is required */
} DDRP_MsgAssign;

/* -------------------------------------------------------------
 * 5. REJECT: Immediate rejection notification
 * ------------------------------------------------------------- */
typedef struct __attribute__((packed)) {
    uint32_t    challenge_id;
    uint8_t     error_code;      /* 0x01: Invalid token, 0x02: Incorrect HMAC,
                                    0x03: Role denied, 0x04: Subnet full */
} DDRP_MsgReject;

#endif /* DDRP_H */

```

### 3. The 4-Way Binary Registration Flow

Without the cost of TCP or SSL establishment, the entire exchange takes less than **2 milliseconds**:

```text
[New Node]                                                       [VANGUARD]
    |                                                                |
    |--- 1. DDRP_PKT_SOLICIT --------------------------------------->|
    |    (DeviceType, PubKey, TokenHash, Hostname)                   |-- Validates if TokenHash exists
    |                                                                |-- Generates 32-byte Nonce
    |<-- 2. DDRP_PKT_CHALLENGE --------------------------------------|
    |    (ChallengeID, Nonce)                                        |
    |                                                                |
    |-- Computes HMAC_SHA256(Token, Nonce)                           |
    |--- 3. DDRP_PKT_RESOLVE --------------------------------------->|
    |    (ChallengeID, HMACProof)                                    |-- Validates authenticity
    |                                                                |-- Chooses Coord X according to DeviceType
    |                                                                |-- Reserves free Coord Y
    |                                                                |-- Injects Peer into WireGuard
    |                                                                |-- Configures rules in nftables
    |<-- 4. DDRP_PKT_ASSIGN -----------------------------------------|
    |    (LCoord(X,Y), AssignedIPv6, GatewayPubKey, WireGuardPort)   |
    |                                                                |
 [Brings up wg0 with the IPv6 and VANGUARD Peer]                [Registration Complete]

```

### 4. Arithmetic Mapping of LCoord to IPv6 in Memory

To avoid slow text string translation (such as `inet_pton`), VANGUARD builds the IPv6 address by manipulating the raw bytes:

- **DENSA Prefix:** `fd00:densa:` (48 fixed bits: `0xfd, 0x00, 0xde, 0xad, 0xbe, 0xef` or `fd00:0de0::`)
- **Injection of `X` (Quadrant / Role):** The 32 bits of `x` are placed in the intermediate positions.

- **Injection of `Y` (Node Identifier):** The 32 bits of `y` are placed in the last 4 bytes of the vector.

```c
void ddrp_compute_ipv6(DDRP_LCoord coord, uint8_t ipv6_out[16]) {
    /* Base ULA Prefix fd00:de00::/32 */
    ipv6_out[0] = 0xfd; ipv6_out[1] = 0x00;
    ipv6_out[2] = 0xde; ipv6_out[3] = 0x00;

    /* Quadrant X (Functional Subnet / Lobe) */
    ipv6_out[4] = (coord.x >> 24) & 0xFF;
    ipv6_out[5] = (coord.x >> 16) & 0xFF;
    ipv6_out[6] = (coord.x >> 8)  & 0xFF;
    ipv6_out[7] = (coord.x)       & 0xFF;

    /* Network padding to zeros */
    ipv6_out[8]  = 0x00; ipv6_out[9]  = 0x00;
    ipv6_out[10] = 0x00; ipv6_out[11] = 0x00;

    /* Node Identifier Y */
    ipv6_out[12] = (coord.y >> 24) & 0xFF;
    ipv6_out[13] = (coord.y >> 16) & 0xFF;
    ipv6_out[14] = (coord.y >> 8)  & 0xFF;
    ipv6_out[15] = (coord.y)       & 0xFF;
}

```

### 5. The Bouncer's Role After `ASSIGN`

At the very instant VANGUARD emits the `DDRP_PKT_ASSIGN` packet, it performs two atomic operations at the operating system level:

1. **Injection into the WireGuard driver:**

```bash
wg set wg0 peer <client_pubkey> allowed-ips <assigned_ipv6>/128

```

2. **Coordinate Registration in the Policy Table:**
   VANGUARD stores the tuple `(X, Y, PubKey, ExpirationTime)`. Since the firewall already has preloaded rules based on quadrant `X`, the device becomes immediately classified and restricted without the need to restart interfaces or reload complex firewalls.
